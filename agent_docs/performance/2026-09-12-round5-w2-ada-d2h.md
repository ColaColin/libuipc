# Round 5, w2-ada — the D2H round trips, measured per call site (RTX 4060 Ti, cc 8.9)

Worker: `w2-ada`, branch `perf/round5-w2-ada` off `perf-round5-base` (`890482c2`).
Box: vast.ai 50737976, RTX 4060 Ti 16 GB, driver 595.71.05, CUDA 12.8, 20 cores / 62 GB.

Round 4's s14 gap attribution said: **24–30 blocking device-to-host reads per Newton iteration,
1.3–3.0 ms per frame of GPU idle on every scene**, and ranked it the only candidate that pays on all
four benchmarks. It did not say *which* reads, because nothing in the tree could tell it.

## 1. The instrument

Every blocking readback in the CUDA backend went through one of four inlined copies of
`cudaMemcpyAsync(<pageable host dst>, …, D2H); cudaStreamSynchronize(…)` in `cuda_tool`
(`DeviceVar::operator T`, `DeviceVector::copy_to`, `CBufferView::copy_to`, `CVarView::copy_to`) plus
one hand-written copy in `abd_linear_subsystem.cu`. They are now one function,
`cuda_tool::host_read` (`src/backends/cuda/cuda_tool/host_sync.h`), which under
`UIPC_D2H_PROFILE=1` splits each readback's wall cost in two:

- **drain** — time spent waiting for work that was still queued. The GPU was *not* idle.
- **stall** — the readback measured with the stream already drained. This *is* the GPU-idle gap.

`UIPC_D2H_PROFILE=2` additionally attributes every readback to its call stack
(`backtrace` + `dladdr`, Linux only, probe only — its own cost makes those runs' wall times
meaningless, only the distribution is read).

That split matters: the naive "time inside the blocking read" is dominated by drain and says
nothing. On mas-bunny, drain is 51.4 ms per 53.8 ms frame (the GPU is ~95 % busy, as round 4 found);
stall is 1.2 ms.

## 2. What the reads actually are

`UIPC_D2H_PROFILE=2`, mas-bunny, 12 frames, 24 Newton iterations, 580 readbacks
(`n` = readbacks, per Newton iteration in brackets):

| n | per Newton it. | stall | site |
|---:|---:|---:|---|
| 144 | 6.0 | 1 031 µs | `LinearFusedPCG::fused_pcg` — 5 block convergence checks (`d_rz_new`, `check_interval`=5) + 1 initial `d_rz` |
| 144 | 6.0 | 891 µs | `InfoStacklessBVH::prepare_query_result` — the two-phase **broad-stage capacity counter**, one read each |
| 72 | 3.0 | 499 µs | `InfoStacklessBVHSimplexTrajectoryFilter` — the batched 4-candidate-count read (s04) |
| 48 | 2.0 | 362 µs | `MatrixConverter` — CUB `RunLengthEncode` unique counts (buffer sizing) |
| 36 | 1.5 | 242 µs | `EasyVertexHalfPlaneTrajectoryFilter` counts |
| 36 | 1.5 | 226 µs | `LineSearcher::compute_energy` — one batched read of all reporter energies |
| 24 | 1.0 | 174 µs | `GlobalTrajectoryFilter::filter_toi` — one batched read of all filter TOIs |
| 24 | 1.0 | 165 µs | `GlobalVertexManager::compute_axis_max_displacement` |
| 24 | 1.0 | 151 µs | `GlobalVertexManager` ← `MaxTranslationChecker::do_check` (convergence residual) |
| 12 | — | **4 654 µs** | `FiniteElementMethod` ← `SimEngine::event_write_scene` — 460 KB of vertex state, **once per frame**, 388 µs each |
| — | — | 33 µs | MAS preconditioner setup, sanity checks, scene init (one-off) |

**≈ 23 blocking readbacks per Newton iteration**, which reproduces round 4's 24–30 exactly.

Two things the ranking settles:

1. **The single most expensive readback is not in the solver at all.** The per-frame scene write-back
   is one 460 KB pageable D2H costing 388 µs — 53 % of all stall in that window. It is fixed by
   staging (below), not by removing a round trip.
2. **Half of the solver's round trips cannot be removed without an algorithmic change**: the PCG
   block convergence check (6/it) and the CUB `RunLengthEncode` counts (2/it) are genuine
   data-dependent host decisions. Raising `check_interval` trades a 14 µs sync for ~5 guarded
   no-op PCG iterations (~8 kernel launches each) — not a trade that wins, and it changes the
   reported iteration count.

## 3. How big the candidate really is on Ada

`UIPC_D2H_PROFILE=1`, default frames, stall = post-drain GPU idle:

| scene | readbacks/frame | stall ms/frame | frame ms | stall share |
|---|---:|---:|---:|---:|
| rigid-wrecking-balls | 94.8 | 0.556 | 31.1 | 1.79 % |
| cube-wall-cloth | 164.8 | 1.046 | 67.9 | 1.54 % |
| mas-bunny | 142.4 | 1.215 | 53.8 | 2.26 % |
| stiff-gipc-case2 | 156.5 | 1.627 | 189.4 | 0.86 % |

So on this box the **entire** candidate — every blocking readback removed — is worth 0.9–2.3 % of
the frame, against round 4's 1.5–3.5 % estimate on a 2070 SUPER. The per-readback cost is 5.9–10.4 µs
here, not the 14–22 µs round 4's nsys gap attribution charged (that gap also contained the host's
decision and the next launch, which a faster host partly hides).

## 4. What was changed

Two commits, both value-identical, both with an env switch back:

1. `UIPC_HOST_SYNC_FAST=0` — pinned, chunked staging for every readback instead of the driver's
   pageable bounce buffer. 6.05 → 5.58 / 6.35 → 5.88 / 8.60 → 8.00 µs per readback, and the 460 KB
   frame write-back becomes a pinned DMA. **Proof of identity**: `UIPC_HOST_SYNC_VERIFY=1` reads
   every value through both paths and memcmps — 860 readbacks on mas-bunny, **0 byte mismatches**.
2. `UIPC_BVH_BATCH_COUNTS=0` — the four broad-stage counters travel in the batched count transfer
   that s04 already built, and the generic BVH paths read their two counters together.
   **Proof of identity**: `UIPC_BVH_BATCH_COUNTS_VERIFY=1` re-reads each counter the old way and
   compares — 2 000+ checks per scene on three scenes, **0 mismatches**. Same values at the same
   point of the stream ⇒ same capacity decisions ⇒ same candidate sets.

## 5. Cross-architecture expectation

Host-latency work, so it is architecture-independent in absolute terms and grows in relative terms
as the GPU gets faster: the same ~0.24 ms/frame of removed stall is 0.45 % of mas-bunny here and
would be ~0.9 % if the 5090 halves the frame. It cannot regress another architecture — the readbacks
it removes were unconditional. The one caveat is the *host*: the per-readback cost is a property of
the CPU and driver, so a slower host box pays more for the reads that remain.

## 6. Candidates this leaves behind

1. **The per-frame 460 KB `event_write_scene` readback** (388 µs/frame pageable, one per frame, 53 %
   of all stall in the probe window) — now pinned, but it is still a full serialisation point at the
   end of every frame. If the application does not need the vertex state every frame, or can take it
   one frame late, this is the single largest host-side item in the pipeline.
2. **The PCG block convergence check** (6/it, the largest solver group). Removing it needs the flag
   in *mapped* host memory with the host spinning on a cache line instead of syncing the stream —
   ~1–2 µs instead of 5–14 µs, and no stream drain. Worth ~0.35 % of the frame on mas-bunny.
   Estimated, not measured.
3. **The `MatrixConverter` RunLengthEncode counts** (2/it) — needs device-side sizing to remove.
4. `EasyVertexHalfPlaneTrajectoryFilter` (1.5/it) and the two `GlobalVertexManager` reductions
   (2/it) are batchable the same way the BVH counters were, for ~3 more of the 23.
