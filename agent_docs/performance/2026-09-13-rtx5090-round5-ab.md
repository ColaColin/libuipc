# Round-5 acceptance: `perf-round5-base` vs `perf/round5` on a rented RTX 5090

Development GPU is not target GPU (`PERF_METHOD.md` §6). Round 5 was developed on four
architectures — Turing cc 7.5 (local), Ampere cc 8.6, Ada cc 8.9, Blackwell cc 12.0 — and every
accepted step carries an explicit, falsifiable claim about whether its gain would transfer to the
acceptance target. This is the measurement that tests those claims.

## Setup

| | |
|---|---|
| GPU | **NVIDIA GeForce RTX 5090**, 32 607 MiB, 3 090 MHz, driver 595.71.05 |
| Box | Vast.ai instance 50832041, 40 vCPU / 251 GB, **$0.611/h** |
| Base | `perf-round5-base` = `890482c2` (round-4 head, after its own acceptance A/B) |
| Head | `perf/round5` = `31ff6a05` (11 accepted steps, cleanup, validation) |
| Build | **both trees on the same box**, same toolchain, CUDA 12.8, `UIPC_CUDA_ARCHITECTURES=native`, shared vcpkg tree |
| Protocol | **5 repetitions, interleaved** base/head per scene, manifest default frame counts |
| Wall clock | 3 804 s from create to destroy; charged ≈ **$0.63** |

Raw records: `data/2026-09-13-rtx5090-round5/` (50 benchmark JSONs, remote timeline, GPU info,
`comparison.md`). Archived the same day, before the instance was destroyed.

n = 5 per arm. **Per-arm ranges are disjoint on all four scenes** (e.g. wrecking-balls base
28.8-29.7 against head 19.9-20.8). **Iteration counts are unchanged** — the largest movement is
+1.1 PCG per frame on case2, i.e. +0.4 %, against a −25.4 % wall change — so these are throughput
results, not trajectory artefacts.

## The transfer prediction, tested

The round's central claim was that its largest family (grid-versus-machine-size: s20, s21/s24, s28)
should pay **more** on a bigger GPU, because a grid of 3 blocks holds 8 % of a 36-SM part but 1.8 % of
a ~170-SM one — while the occupancy-shaped work (s30, and the wave-quantisation half of the hinge
win) should shrink or invert. Two workers made that argument independently from cc 7.5 and cc 12.0.

| scene | validation, cc 7.5 | **acceptance, cc 12.0** | direction |
|---|---:|---:|---|
| rigid-wrecking-balls | −27.8 % | **−30.1 %** | **larger** |
| cube-wall-cloth | −20.9 % | **−26.7 %** | **larger** |
| stiff-gipc-case2 | −16.6 % | **−25.4 %** | **larger** |
| mas-bunny | −9.1 % | **−6.6 %** | **smaller** |

**Three of four scenes gained more on the target, and the fourth is the one the round predicted would
gain less.** mas-bunny is the SNH-dominated scene — the home of s29/s30, whose author flagged s30 as
R3's category ("the 5090 is *more* arithmetic-bound at 1/64 FP64, which makes latency hiding worth
less, not more; expect a smaller win, and zero or negative is possible"). It is smaller, and still
positive.

This is the strongest evidence the round produced, because it was **written down before it was
measured** and could have come out the other way.

## What this does not establish

- **Per-step attribution on this GPU.** These are composed numbers. The per-step splits in the ledger
  are cc 7.5 / 8.6 / 8.9 / 12.0 development measurements, and no per-step A/B was run here.
- **`UIPC_GRID_SPREAD_ONLY` cannot isolate s20 from s24** (validation §5), so even a follow-up arm on
  this hardware could not cleanly separate them without a code change.
- **R6 and R7 were not tested here.** Both ship default-off and both carry a specific prediction that
  they may win on a 5090 (R6's idle-block share grows with bandwidth; R7's fold cost is per-wave and
  ~5x cheaper at 170 SMs). Each is a one-variable arm — `UIPC_SPMV_GRID_STRIDE=1`, and
  `UIPC_PCG_FOLD=1 UIPC_PCG_FOLD_MAXGRID=0` — for whoever rents the next box.
- **One box, one session.** Five interleaved repetitions on a single rented machine; no cross-host
  replication.

## Cost

Three earlier attempts failed before this one, for two distinct reasons, both now fixed:
a host that could not reach Docker's registry (`vast_run_5090.sh` gave up rather than taking the next
offer), and — the expensive one — **`FAILED: resolve perf-round5-base`**: round 4's base ref was a
*tag*, which a clone fetches by default, while round 5's is a *branch*, which exists only as
`refs/remotes/origin/<name>` and does not resolve through `git rev-parse --verify <name>`. The remote
script fetched `HEAD_REF` explicitly but never `BASE_REF`. Each failure paid for an instance, apt and
a clone before reaching the failing line: ≈ $0.15 and 25 minutes across three boxes. Both the fetch
and a **pre-flight ref check that refuses to rent when a ref is missing** are in `tools/vast/`.

Round-5 total spend: **$4.41** against a $5.00 authorisation.
