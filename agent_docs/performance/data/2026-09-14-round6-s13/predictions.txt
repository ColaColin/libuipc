P1 (scope). The fitted grid removes exactly the blocks grid-stride removes, so the per-launch delta
   should land on grid-stride's: case2 -6 to -7 %, mas-bunny -1.8 to -2.2 %. It may beat grid-stride
   slightly (one pass per block, no loop, more blocks available to hide latency) or lose slightly
   (grid-stride's 160 blocks are exactly resident; 1 120 blocks is 7.0 waves on case2 but 3.14 on
   mas-bunny, i.e. a tail).

P2 (end to end). SpMV is 18.16 % of case2 and 28.8 % of mas-bunny kernel time, so
   case2 -1.1 to -1.3 % and mas-bunny -0.5 to -0.6 % of the wall. Both below 2 %: n >= 8, and the
   null arm in the same sweep. Unlike R6 the iteration counts must NOT move systematically -- the
   fitted grid feeds the same triplets to the same (blockIdx, threadIdx) and issues the same
   multiset of atomicAdds -- so the harness's guard should stay silent and any count drift should
   sit inside mas-bunny's own PCG envelope (35 185 - 35 225 over ten baseline runs, 0.11 %).

P3 (the other two scenes). Round 4 recorded rigid-wrecking-balls at <= 32k unique triplets against
   a > 4M capacity, i.e. ~99 % idle blocks -- the largest relative idle share in the suite -- but
   its SpMV is only ~9.9 us/launch (round 5). Predict the largest *relative* per-launch win there
   (> 15 %) and a small end-to-end effect. cube-wall-cloth in between.

P4 (graph rebuilds). With 12.5 % headroom and a 64-block quantum the fitted grid should take
   <= 3 distinct values over a 250-frame case2 run and exactly 1 on mas-bunny, so the added key
   term should cost at most a handful of extra captures per run.

P5 (transfer). Category: grid-size against machine-size. The idle-block *count* is a property of
   the matrix (capacity/nnz), not of the GPU, and the working part of the launch gets faster on a
   bigger GPU -- so the idle share, and therefore the win, should GROW. Round 5 R6 made the same
   prediction and it has still never been tested on a 5090.
