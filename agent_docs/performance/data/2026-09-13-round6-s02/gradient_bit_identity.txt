Device-side both-paths comparison of the hinge GRADIENT (PERF_METHOD §2.3).

UIPC_DSB_GN_VERIFY=1 (shipped, zero cost when off) makes
DiscreteShellBending::do_compute_gradient_hessian launch the *real* shipped
kernel <Proj=1, Solver=1> first, snapshot the gradient doublets it wrote
(values + indices) into a device shadow buffer, then launch <Proj=3, Solver=1>
over the same inputs, then compare every 32-bit word on device and accumulate
the mismatch count. This is the repo's own SpreadVerifier machinery (round 5,
s24); the live state after the pair is the Gauss-Newton launch's, so the run
continues on the shipped path while it is being checked.

This is a comparison of the two shipped kernel BINARIES on real simulation
inputs -- not a source-level "same expressions" argument, which PERF_METHOD
§2.3 explicitly rejects.

The ENERGY is bit-identical for a stronger reason: it is a different kernel
(DiscreteShellBending_do_compute_energy_kernel), this step does not touch it,
and its SASS instruction stream hashes identically to main's -- see
sass_identity.txt.

mas-bunny and rigid-wrecking-balls print nothing because the hinge kernel never
launches in them (scene_executes_kernel.txt) -- they are untargeted-regression
controls only, never evidence of a win.
