### Reading of the profile (targets for this round)

1. `Spmv_rbk_sym_spmv_dot_kernel` is the largest kernel in every scene (43 / 29 / 47 / 20 %), yet
   its cost does not track nnz: 1.54 ms per launch on the wrecking balls with at most 32k unique
   triplets. The launch grid covers `bcoo_A.triplet_capacity()` (graph-stable shape), and that
   capacity is reserved from the *raw* triplet count (1.5x), which for ABD contacts is 16x the
   contact block count — so > 99 % of the blocks find no triplet and still run three empty warp
   reductions, a block barrier and an `atomicAdd(+0.0)`. Same mechanism in the other scenes at
   a smaller ratio (raw/unique = 3-4x for FEM meshes). → s02.
2. `abd_linear_subsystem_assemble_dytopo_effect_k2_kernel`: 29 ms per launch on the wrecking balls
   (29 % of GPU), 3.9 ms on cube-wall, for ~200k contact 3x3 blocks. ptxas: 255 registers, 7 104 B
   stack frame, 3.1 KB spills. Cost attribution on the wrecking balls (60 frames, four variants of
   the kernel launched on the same inputs in one nsys run, ms per launch): dense kernel as is 33.9;
   extern `ABDJacobi::JT_H_J` (defined in `abd_jacobi_matrix.cu`, an RDC cross-TU call returning a
   12x12 through the stack, two calls per block) replaced by an inlined copy → 8.9; additionally
   the `TripletMatrixUnpacker` write replaced by direct block stores → 4.9; no `JT_H_J` at all but
   the unpacker write → 13.8. The 144 same-address atomics into `diag_hessian(body)` (7 of the 10
   blocks of a PT pair are intra-body) are *not* the bottleneck: removing them changes the kernel
   by < 1 ms (see Rejected). → s01 (inline `JT_H_J`).
3. Triplet-buffer traffic on the ABD scenes: raw 3x3 triplets = 16 per contact block; fill, ge2sym
   k1/k2, sort k3 and the segmented reduce each stream ~0.3-0.4 GB per Newton iteration on the
   wrecking balls (≈ 10 ms/it "Convert To BCOO" + 1.7 ms fill). A per-body-pair pre-reduction
   (sum the contact blocks of one (body_i, body_j) pair before expanding to 16 triplets) is the
   structural fix; it changes the summation order (rounding-level).
4. Broad phase: `stacklessSelf [AllE_AllE]` 5.6 ms/launch on case2 (9.8 %), 2.8 ms on the wrecking
   balls, 2.0 ms on cube-wall; `stacklessOther [AllP_AllT]` 2.9 ms on case2. K11's range cull is
   already in; the remaining cost is the warp-divergent traversal itself.
5. FEM constitutions on case2 / cube-wall: bending 5.1 / 4.5 ms per launch (K16 is in),
   SNH 4.8 / 2.4 ms — FP64-bound.
6. `abd_diag_preconditioner_do_apply_kernel` on cube-wall: 0.103 ms x 20k launches (10.9 %) for
   1 920 bodies — one thread per body doing a 12x12 matvec in FP64 (8 blocks of 256 for the whole
   GPU); a warp- or 12-lane-per-body layout would parallelise it.
7. MAS on case2 / bunny: `schwarz_local_solve` 66 / 32 µs per PCG iteration plus
   `scatter_hessian_to_clusters` 2.4 / 1.2 ms and `invert_cluster_matrices` 1.8 / 0.8 ms per Newton
   iteration.
8. Build note: `build-perf` (Release) compiles with `UIPC_RUNTIME_CHECK=1` (the project default), so
   every `UIPC_KERNEL_ASSERT` (view bounds checks, unpacker range checks) is live in these kernels.

Candidate 1 below is done (s03). Updated ranking for the next steps: (a) BVH `stacklessSelf` — now the

## Rejected / reverted

- **s01 first attempt — ABD diag preconditioner block gathered from the BCOO matrix** (`UIPC_ABD_DIAG_FROM_BCOO`):
  hypothesis was that the 144 same-address atomic doubles per intra-body contact block into
  `diag_hessian(body)` made the dytopo k2 kernel slow. Implemented (gather kernel with one lower_bound
  per block row, 60 µs/launch; atomics skipped in the reporter/dytopo kernels), full gate passed, but no
  gain: k2 34.66 → 35.61 ms per launch with the atomics removed (wrecking balls, 60 frames, nsys), official
  rigid-wrecking-balls 378.3 / 378.1 (old) vs 380.7 / 396.2 (new) ms/frame, cube-wall 190.5 / 191.9 vs
  186.6 / 192.4; re-checked on the inlined kernel later: 10.5 / 10.7 ms with atomics vs 11.3 / 11.4 without
  (rounding-level change of the preconditioner, no measurable gain) — reverted.
- **s01 variant — per-block evaluation of `J^T H J`** (16 blocks computed and stored one at a time,
  no 12x12 temporary; 104 registers, 96 B stack, no spills): 10.2 – 12.0 ms per launch vs 7.1 ms for the
  inlined dense kernel on the same contact population (ge2sym k1 3.4 – 3.6 ms in every run) — slower,
  not adopted. The dense kernel with the inlined call also tried with direct block stores instead of
  `TripletMatrixUnpacker::block<4,4>().write` (`UIPC_ABD_DYTOPO_DIRECT_STORE`): 7.11 / 6.80 vs 7.14 ms —
  no gain, removed. (In the four-variant attribution run the unpacker looked 2x more expensive than
  direct stores, but that was measured on the *extern-call* kernel; with the call inlined the
  difference vanishes.)
