### Reading of the profile (targets for this round)

1. `Spmv_rbk_sym_spmv_dot_kernel` is the largest kernel in every scene (43 / 29 / 47 / 20 %), yet
   its cost does not track nnz: 1.54 ms per launch on the wrecking balls with at most 32k unique
   triplets. The launch grid covers `bcoo_A.triplet_capacity()` (graph-stable shape), and that
   capacity is reserved from the *raw* triplet count (1.5x), which for ABD contacts is 16x the
   contact block count — so > 99 % of the blocks find no triplet and still run three empty warp
   reductions, a block barrier and an `atomicAdd(+0.0)`. Same mechanism in the other scenes at
   a smaller ratio (raw/unique = 3-4x for FEM meshes). → s02.
2. `abd_linear_subsystem_assemble_dytopo_effect_k2_kernel`: 29 ms per launch on the wrecking balls
   (29 % of GPU), 3.9 ms on cube-wall, for ~200k contact 3x3 blocks. ptxas: 255 registers, 7 104 B
   stack frame, 3.1 KB spills. Cost attribution on the wrecking balls (60 frames, four variants of
   the kernel launched on the same inputs in one nsys run, ms per launch): dense kernel as is 33.9;
   extern `ABDJacobi::JT_H_J` (defined in `abd_jacobi_matrix.cu`, an RDC cross-TU call returning a
   12x12 through the stack, two calls per block) replaced by an inlined copy → 8.9; additionally
   the `TripletMatrixUnpacker` write replaced by direct block stores → 4.9; no `JT_H_J` at all but
   the unpacker write → 13.8. The 144 same-address atomics into `diag_hessian(body)` (7 of the 10
   blocks of a PT pair are intra-body) are *not* the bottleneck: removing them changes the kernel
   by < 1 ms (see Rejected). → s01 (inline `JT_H_J`).
3. Triplet-buffer traffic on the ABD scenes: raw 3x3 triplets = 16 per contact block; fill, ge2sym
   k1/k2, sort k3 and the segmented reduce each stream ~0.3-0.4 GB per Newton iteration on the
   wrecking balls (≈ 10 ms/it "Convert To BCOO" + 1.7 ms fill). A per-body-pair pre-reduction
   (sum the contact blocks of one (body_i, body_j) pair before expanding to 16 triplets) is the
   structural fix; it changes the summation order (rounding-level).
4. Broad phase: `stacklessSelf [AllE_AllE]` 5.6 ms/launch on case2 (9.8 %), 2.8 ms on the wrecking
   balls, 2.0 ms on cube-wall; `stacklessOther [AllP_AllT]` 2.9 ms on case2. K11's range cull is
   already in; the remaining cost is the warp-divergent traversal itself.
5. FEM constitutions on case2 / cube-wall: bending 5.1 / 4.5 ms per launch (K16 is in),
   SNH 4.8 / 2.4 ms — FP64-bound.
6. `abd_diag_preconditioner_do_apply_kernel` on cube-wall: 0.103 ms x 20k launches (10.9 %) for
   1 920 bodies — one thread per body doing a 12x12 matvec in FP64 (8 blocks of 256 for the whole
   GPU); a warp- or 12-lane-per-body layout would parallelise it.
7. MAS on case2 / bunny: `schwarz_local_solve` 66 / 32 µs per PCG iteration plus
   `scatter_hessian_to_clusters` 2.4 / 1.2 ms and `invert_cluster_matrices` 1.8 / 0.8 ms per Newton
   iteration.
8. Build note: `build-perf` (Release) compiles with `UIPC_RUNTIME_CHECK=1` (the project default), so
   every `UIPC_KERNEL_ASSERT` (view bounds checks, unpacker range checks) is live in these kernels.

### s04 probe of the BVH self traversal (2070S, after s03)

`UIPC_BVH_SELF_STATS=1` (kept as a probe) launches a traversal-only copy of the self kernel after the real one
(same inputs, no leaf predicate, no output) and prints per-launch counters. Wrecking balls (30 frames, 123 launches,
27 954 edge queries): 1.95 M node visits per launch (70 per query; 178 k range-culled, 383 k box-missed, 78 k
node-culled), 350 k ordered leaf pair tests (12.5 per query), 44 k hits. case2 (40 frames, 233 launches, 74 912
queries): 6.8 M visits (91 per query), 1.24 M pair tests (16.6 per query; the largest launch 13.4 M / 4.0 M), 275 k
hits, no node culls. nsys per launch, real vs traversal-only: wrecking balls 3.55 vs **0.19 ms**, case2 4.40 vs
**0.36 ms** — the leaf predicate (16+ scattered loads, FP64 edge-edge geometry, executed warp-divergent at the leaves,
≈ 8 ns ≈ 500 SM-cycles per test) is 92–95 % of the kernel; the pointer-chasing traversal itself is cheap. ptxas: self

### s09 findings on the cluster-matrix inverse (2070S)

The old `invert_cluster_matrices` kernel is a textbook in-place Gauss-Jordan with the identity
substituted into the pivot column, one thread per column, the whole 48x48 float matrix in shared
memory. Two structural facts make it 4x slower than it needs to be: (1) the rank-1 update
`s_mat(row,col) += factor * s_mat(pivot,col)` touches only the thread's *own* column, so the shared
array is used as a private scratch pad — four shared accesses per FMA, and 18 816 B per 96-thread
block caps the SM at 3 blocks = 9 warps (28 % occupancy); (2) the only genuinely shared datum is the
pivot column, which in the identity-substituted form lives entirely in one thread. Switching the
elimination to the symmetric sweep operator makes the working matrix stay symmetric, so the pivot
column *is* the pivot row and each thread publishes exactly one float per pivot — which is what lets
the column move into registers. Measured cost split of the new kernel (standalone harness,
1 281 clusters): 199 us total, of which 61 us is the load of the 9.4 KB FP64 cluster Hessian plus the
6.3 KB FP32 store (18.3 MB at ~300 GB/s, i.e. already at the DRAM roof), leaving ~140 us for
48 x 48 x 48 FMA + broadcast loads. Removing the barriers entirely does not help (228 us), `float4`
shared reads do not help (209 vs 211 us at 96 threads): what moved the needle was occupancy
(9 -> 18 warps) and dropping the shared traffic per FMA from 4 to 1.

Latent bug found on the way: the old kernel has a cross-warp race. After the second
`__syncthreads()` of a pivot step every thread writes `s_mat(col, pivot)` (zeroing the pivot column)
while thread `pivot` reads and updates that same column in its own row loop; nothing separates the
two. In a standalone harness on random SPD matrices (A = BB^T + 48I) it corrupts 4-7 of 1 281
cluster inverses per launch, non-deterministically (residual `||A A^{-1} - I||_inf` up to 1.3e+1
against 8.5e-7 for the clean clusters); inserting one `__syncthreads()` after the pivot-column write
removes it and makes old and new agree to 2.7e-7 relative. In situ on the benchmark scenes the race
appears benign (`UIPC_MAS_INVERT_VERIFY=2` on the old path reports bit-identical output over 20
Newton iterations), so it is not the reason for the speed-up, but the old path should not be revived
without the missing barrier. The sweep kernel cannot race: the only shared object is the pivot row,
written once per thread per pivot and read after the barrier.

### s13 findings on the MAS apply kernels (2070S, after s12)

The post-s12 candidate (c) proposed two levers for `schwarz_local_solve`: a smaller
(symmetric) inverse representation, and fusing the three apply kernels. Both were examined
before any code was written, and both turn out to be closed:

1. **The cluster inverse is already stored as the symmetric upper triangle.**
   `ClusterMatrixSymT` holds `SYM_BLOCK_COUNT = BANKSIZE*(BANKSIZE+1)/2 = 136` 3x3 blocks, not
   16x16 = 256, and `sym_index(row, col)` is the upper-triangle addressing that the local solve,
   the scatter and the inverse all use. 136 blocks x 9 floats x 4 B = 4 896 B per cluster; x 1 281
   clusters = 6 271 776 B = exactly the **6.27 MB** that s08 and s12 measured. Full storage would be
   11.8 MB. The only further compaction symmetry offers is the 6 redundant off-diagonal floats of
   each of the 16 *diagonal* 3x3 blocks (1 224 -> 1 176 floats per cluster, **-3.9 %**), which does
   not pay for the extra indexing. So "halve the 6.27 MB re-read by storing only the upper
   triangle" is void — it is what the code already does.
2. **Sector accounting puts the local solve at ~87 % of the DRAM roof.** In the s12 row-dot kernel
   thread `t = 3*row + comp` of a cluster reads, at column `c`, either `M[sym_index(row,c)](comp, 0..2)`
   (row <= c) or `M[sym_index(c,row)](0..2, comp)` (row > c). The second form lands at
   `panel_base(c) + t*12` bytes — **perfectly coalesced** across the 48 threads of the cluster. The
   first form has each 36-byte block touched by only 3 lanes, at a `~(15-row)*36` B stride between
   rows, so its 32-byte sectors are over-fetched ~1.8x. Weighting the two halves gives ~1.4x, i.e.
   ~8.8 MB of sector traffic per launch: 8.8 MB / 27.6 us = **318 GB/s** against the 365 GB/s DRAM
   figure of s07. Making *both* halves coalesced requires both a row-panel and a column-panel copy
   of the inverse (2x memory, 2x DRAM), so the layout lever is closed too — which is why the three
   s08 relayouts and the s12 row-dot all land within 15 % of each other.
3. **Clusters per block was never swept** (s12 fixed it at 2). `UIPC_MAS_LOCAL_SOLVE_CPB`, nsys,
   bunny 20 frames, us per launch: 1 -> 28.30, **2 -> 27.94**, 4 -> 27.91, 8 -> 29.43, 16 -> 34.01.
   The existing default is already optimal; the knob is kept as a probe.
4. **A grid-synchronising fusion of the three apply kernels is not launchable at these shapes.**
   Per PCG iteration the apply is `build_multi_level_R` (80 blocks x 256 on the bunny, 178 on case2)
   -> `schwarz_local_solve_rowdot` (**686** blocks x 96 on the bunny, **1 522** on case2) ->
   `collect_final_Z` (81 / 180 x 256). The restriction must finish for *all* fine nodes before any
   coarse cluster is solved, and all levels must be solved before any fine node is collected, so a
   single kernel needs two grid-wide barriers. A cooperative launch caps the grid at the
   simultaneously resident blocks — at most 16 blocks/SM x 40 SMs = 640, and with 3 warps per block
   the 32-warp limit gives 10/SM = 400 — so even the bunny's 686-block local solve exceeds it; the
   fusion would need a persistent-block rewrite. And the prize is small: the s11 graph-node trace
   measured the gaps between two ordinary kernel nodes inside the replayed block at **0.16-0.22 us**,
   and the only traffic a fusion removes is the `multi_level_R` fine round-trip (0.25 MB write +
   0.25 MB read) and the `multi_level_Z` fine round-trip (0.23 + 0.23 MB) — ~1.3 us of the 46.6 us
   the three kernels cost, against two grid barriers. Not implemented.
5. What a fusion *would* have removed for free is the one remaining whole GPU node of the apply that
   exists only to zero memory: the coarse `multi_level_R` fill, **1 432 ns per PCG iteration for
   15 KB** (1 296 Vector3f). That was taken instead — see s13b — by letting the tail threads of
   `collect_final_Z` re-zero the accumulator for the *next* apply.

### s14 findings: the K7/K16 translation-free hinge projection was never applied to the plain `DiscreteShellBending`

Round 3 introduced `make_spd_translation_free_4x3` (K7) and its block-assembled form
`make_spd_translation_free_4x3_blocked` (K16) in `utils/make_spd.h` for the hinge Hessian of the
**Dahl friction** discrete-shell bending constitution (the cloth-dataset scenes). The plain
`DiscreteShellBending` — the constitution the *official* benchmarks use, and after s13 the single
largest kernel of the whole suite (cube-wall 28.1 %, case2 12.9 %) — still called the generic
`make_spd<12>` 12x12 eigen-solve, and `make_spd_translation_free_4x3_blocked` had no caller at all.
Nothing in the round-3 or round-4 records connects the two: round 3 profiled the Dahl hinge, round 4
never looked inside this kernel.

The precondition holds verbatim: `sym::discrete_shell_bending::ddEddx` builds
`H = ddEddtheta * g g^T + dEdtheta * ddthetaddx` from the dihedral angle only, and the dihedral angle
is translation invariant, so `H t = 0` exactly for every rigid translation `t`. Device verifier
(`s14/verify_dsb.cu`, 200 000 randomized hinges through the real `DSB::ddEddx`, half of them
translated by a random offset of up to 10 length units, kappa up to 2e5): max
`||H t||_inf / ||H||_inf = 6.4e-13`, max relative difference between `make_spd<12>(H)` and
`make_spd_translation_free_4x3_blocked(H)` = **1.28e-13**, same against the dense K7 form; no NaNs,
no negative diagonal in the projected result.

### Candidates after s14

(a) **The same projection for the two plastic discrete-shell bending constitutions**
(`strain_plastic_discrete_shell_bending.cu:128`, `stress_plastic_discrete_shell_bending.cu:128`)
— identical `make_spd(H12x12)` on a dihedral-angle-only hinge energy, so the s14 argument and
verifier carry over one-to-one. Neither appears in the four official scenes, so it is a
correctness-preserving cleanup with no measurable benchmark effect here; it is the cheapest
remaining item and would pay off on any scene that uses plasticity.
(b) [taken as s15, partly] **`StableNeoHookean3D` G/H** (case2 14.1 % at 4.766 ms/launch, bunny 16 % at 2.400) is at its
FP64 roof *for the expression tree it evaluates* (~4 200 FP64 per tet, ~30 ns per thread against
2 FP64/clk/SM), but the tree has redundancy the compiler does not remove at 255 registers: inside
the fully unrolled 10-block loop the stretch-mode matrix `q = U * bv_m.asDiagonal() * V^T`
(54 FP64) is rebuilt for every (block, mode) pair — 30 times per tet instead of 3 — and the two
`q * shape_gradients.col(.)` matvecs (15 FP64 each) are recomputed although `left`/`right` take
only 4 distinct values. Folding them as `w = U * (bv_m .* sa[i]) * sqrt(2)` (note `sa[i]` in the
kernel is already `sV^T g_i`) removes an estimated 1 400-2 900 of the ~4 800 FP64 instructions of
the Hessian part; rounding-level (re-association), verifiable with the same harness style as
`s14/verify_dsb.cu`. This is the largest single remaining kernel of the suite.
(c) [refuted, see the s16 rejection] **`DiscreteShellBending` G/H is still 18.9 % of cube-wall** after s14. The next lever there is
K12-style fusion: the kernel calls `DSB::dEdx` and then `DSB::ddEddx`, and *both* recompute
`dihedral_angle` and `dihedral_angle_gradient` from scratch (the Dahl constitution already has the
fused `DFDSB::dEdx_ddEddx` for exactly this reason). A `dEdx_ddEddx` for the plain constitution is
bit-identical if the shared sub-expressions are evaluated once in the same order.
(d) **IPC simplex normal contact G/H** (`do_assemble_kernel<false,1>` / `<false,2>`) is 30.9 % of
the wrecking balls, 13.4 % of cube-wall, 8.3 % of case2 — the largest family after the FEM
constitutions. K17 (round 3) measured the block-assembled projection for the EE branch as a wash,
but the PT/PE/PP branches were never re-examined at the current 255-register / 3.5 KB-spill shape.
(e) **D2H round trips**: 24-30 blocking device-to-host reads per Newton iteration cost 1.3-3.0 ms
per frame of GPU idle on every scene (see the idle table above). Batching the per-iteration scalars
into one pinned staging buffer read once, or moving the convergence decision device-side, is the
only host-side item worth more than 1 % — and it is worth 1.5-3.5 % on all four scenes at once.
(f) `ortho_potential_compute_gradient_hessian` (wrecking balls 9.6 %, cube-wall 6.6 %) and
`abd_diag_preconditioner_do_assemble` (5.5 / 5.6 %) still run on **3-8 blocks**, i.e. 7-20 % of the
SMs, and are independent of each other inside the same Newton iteration: running them on two streams
would overlap two kernels that each leave 80 % of the GPU idle (s06 ruled out a lane-parallel form,
not the overlap).

### s15 findings: how much redundancy is left in the SNK1 Hessian, and how much the compiler already removes

Post-s14 candidate (b) claimed the fully unrolled 10-block stencil loop of
`StableNeoHookean3D_do_compute_gradient_hessian_kernel` rebuilds the stretch-mode matrix
`q_m = U diag(bv_m) V^T` 30 times per tet instead of 3, and recomputes the 12 contractions
`q_m * shape_gradients.col(i)` 60 times instead of 12. Static SASS counts (`cuobjdump -sass`, sm_75,
`s14/sass_snk1*.txt`) settle how much of that ptxas already removes: the in-loop kernel has
**3 941** FP64 instructions (2 660 DFMA + 1 070 DMUL + 211 DADD) on a straight-line 256-instruction
body, the hoisted one **3 617** — the hoist is worth **324 instructions (-8.2 %)**, i.e. ptxas was
already CSE-ing most, but not all, of the 30 `q_m` builds. Spills drop with it (472 / 876 B ->
248 / 248 B; stack frame 864 -> 976 B, registers 255 either way).

Measured (nsys, ms per launch, `UIPC_SNK1_HOIST_STRETCH` A/B in the same build; bunny 40 frames,
case2 40 frames): SNK1 G/H **2.4037 -> 2.3240 on mas-bunny (-3.3 %)** and **4.7791 -> 4.5493 on
stiff-gipc-case2 (-4.8 %)**; scene kernel time per Newton iteration 14.214 -> 14.153 (-0.43 %) and
29.658 -> 29.423 (-0.79 %). That is below this box's wall-clock noise at the scene level — see the
ledger row for the official-benchmark confirmation that there is no regression. It is kept because
it is bit-identical, strictly fewer instructions and fewer spills, and because the final acceptance
box (RTX 5090, FP64 at 1/64 rate) makes this kernel a *larger* share than it is here.

The rest of the kernel's ~3 600 FP64 instructions break down roughly as: the twist/flip half
60 x (2 x 6 w-builds + 12 rank-1) ~ 1 560; the stretch rank-1 updates 30 x 12 = 360; the hoisted
stretch contractions ~216; and ~1 450 for `qr_svd`, the 3x3 `evd`, `SNH::dEdF` and
`project_F_gradient` — that last block, 40 % of the kernel, is the only part nobody has looked at.
Hoisting the twist/flip w-vectors the same way needs 24 `Vector3` (144 registers) and was not
attempted at 255 registers / 248 B of spills.

  reads the residual through `part_to_real`, i.e. one scattered 24-byte FP64 gather per node, and
  s12's probe attributed 7.2 of the kernel's 13.3 us to the fine-level part. The probe split that
  gather into a separate staging kernel over *real* vertex order (R read perfectly coalesced, the
  float3 scattered into `multi_lr`, which the restriction then reads contiguously; bit-identical —
  the same `static_cast<float>` of the same value; the bank-padding entries are zeroed once per
  Newton iteration instead of every apply, since nothing writes them any more). nsys, bunny 30
  frames, two runs each way, us per PCG iteration: `build_multi_level_R` **13.38 -> 12.68** (-0.70),
  new staging kernel **+4.97**, whole-run kernel time 1 209.1 -> 1 223.4 ms (+1.2 %). So the gather
  is *not* what the fine part of the restriction costs — removing it entirely buys 5 % of the kernel
  — while the scattered 12-byte stores cost 5 us for 0.71 MB (143 GB/s: each 12-byte store dirties a
  32-byte sector). That also caps the variant this record proposed for the next agent (do the
  scatter inside `fused_update_xr`, which already holds `r(i)`): its ceiling is the same 0.70 us,
  against a store cost that is only partly hidden by the kernel it is folded into. Candidate
  refuted, not just unimplemented.
- **s16 candidate — fused `dEdx_ddEddx` for the plain discrete-shell bending hinge**
  (post-s14 candidate (c), `UIPC_DSB_FUSE_GH`). `DiscreteShellBending_do_compute_gradient_hessian_kernel`
  calls `DSB::dEdx` and then `DSB::ddEddx`, and both recompute `dihedral_angle`, `DSB::dEdtheta` and
  `dihedral_angle_gradient` from scratch; the Dahl friction hinge has had the fused
  `DFDSB::dEdx_ddEddx` since round 3 for exactly this reason. A bit-identical `DSB::dEdx_ddEddx` was
  written and measured, and it is a **loss**: the 12-component `dthetadx` and the accumulated `G12`
  have to stay live across the 12x12 `dihedral_angle_hessian`, and at 255 registers that is paid in
  local memory. ptxas on the accepted `Proj = 1` kernel, unfused -> fused: stack frame 3 472 ->
  3 696 B, spill stores 2 456 -> 3 244 B (+32 %), spill loads 2 456 -> 3 468 B (+41 %). nsys, ms per
  launch, two independent A/B pairs on cube-wall-cloth (60 frames) and one on stiff-gipc-case2
  (40 frames): **2.638 -> 2.711 and 2.632 -> 2.696 (cube-wall, +2.4 to +2.8 %)**, **2.469 -> 2.524
  (case2, +2.2 %)**; scene kernel time per Newton iteration 13.951 -> 14.041 and 13.966 -> 14.037.
  Reverted; the saved recomputation is smaller than the extra spill traffic it causes. The same
  fusion remains correct and profitable for the *Dahl* hinge, where it is already in.
