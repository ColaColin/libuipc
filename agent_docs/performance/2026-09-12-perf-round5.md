# Perf round 5 — four parallel workers, one GPU architecture each

Round 4 (`2026-09-12-perf-round4.md`, 17 accepted steps, −45 to −72 % on the official suite on a
5090) ran one worker at a time on one local GPU, because measurements contend. This round buys its
way out of that constraint: **four workers, four GPUs, four disjoint subsystems** — and turns the
fleet into a second deliverable, because the same change is measured on four architectures.

- **Base**: `perf-round5-base` = `890482c2` (round-4 head, after the 5090 acceptance A/B).
- **Brief**: `/workspace/output/round5/AGENT_BRIEF.md` (invariant commands, gates, ownership map).
- **Branches**: `perf/round5-<worker>` per worker, merged into `perf/round5` by the coordinator.
- **Budget**: $5 hard cap, enforced by `tools/vast/vast_budget_guard.sh` (destroys the whole fleet
  when account credit falls below $3.20), plus a 300-minute age backstop.

## Probe p01 (w1-ampere) — what `StableNeoHookean3D` G/H actually spends its FP64 on

Run without a GPU (the box never booted, see the coordinator log): `nvcc` compiles fine headless, so
stage-stubbing plus SASS instruction counting is fully available. Compiled standalone for `sm_75`
with the exact flags from `build-perf/compile_commands.json`. **Rig validated against round 4 first**
— the baseline reproduces s15 exactly (255 regs, 864 B stack / 472+876 B spills for `<false>`,
976 B / 248+248 for `<true>`, FP64 3 941 -> 3 617 on s15's op set, the same -324 delta), and
stubs-off compiles bit-for-bit identically to base.

Shipped path (`HoistStretch=true`), 3 729 static FP64:

| stage stubbed | FP64 | delta | static share |
|---|---|---|---|
| **`math::qr_svd`** | 2 388 | **1 341** | **36.0 %** |
| twist/flip half of the stencil loop | 2 510 | 1 219 | 32.7 % |
| stretch half of the stencil loop | 3 144 | 585 | 15.7 % |
| **`evd<Float,3>`** (3x3) | 3 259 | **470** | 12.6 % |
| `SNH::dEdF` | 3 705 | 24 | 0.6 % |
| `fem::project_F_gradient` | 3 705 | 24 | 0.6 % |

Checked for CSE artifacts: the `qr_svd` stub with `U != V` gives 1 327 instead of 1 341 (1 %), so the
delta is work removed, not downstream collapse.

**Two of the four stages round 4 named are 1.3 % of the kernel combined.** The "~40 % that is not
the stencil loop" is really `qr_svd` + `evd` = 1 811 static FP64 = 48.6 %, and `dEdF` /
`project_F_gradient` should be struck from the pick list.

### The dominant cost is a divergent loop, which a static count charges once

`loops.py` finds **exactly one backward branch in the whole kernel**: a 494-instruction body with
232 FP64 and 12 MUFU at `0x45c0..0x6490`, which vanishes when `qr_svd` is stubbed. It is the
Wilkinson-shift bidiagonal QR iteration in `qr_svd.hpp:245`; everything else is straight-line.
`qr_svd` is `UIPC_GENERIC`, so the real code was instrumented and run host-side, 65 536 samples per
distribution:

| F distribution | mean its | median | p95 | max | warp-max mean |
|---|---|---|---|---|---|
| `I + 1e-4*N` | 3.07 | 3 | 4 | 5 | 4.25 (x1.38) |
| `I + 1e-1*N` | 3.30 | 3 | 4 | 5 | 4.56 (x1.38) |
| full random | 3.34 | 3 | 4 | 5 | 4.57 (x1.37) |
| `R*(I+1e-2*N)` | 3.23 | 3 | 4 | 5 | 4.45 (x1.38) |

The trip count is ~3.2 and strikingly insensitive to the deformation regime, but the loop is
divergent: all 32 lanes pay the warp maximum, ~4.5. **The divergence tax alone is x1.38.**

Warp-effective FP64 (3 729 + 232 x 3.45 = 4 529):

| stage | warp-effective FP64 | share |
|---|---|---|
| **`qr_svd`** (1 095 straight-line + ~1 032 loop) | **2 127** | **47.0 %** |
| twist/flip half | 1 219 | 26.9 % |
| stretch half | 585 | 12.9 % |
| `evd<Float,3>` | 470 | 10.4 % |
| `dEdF` + `project_F_gradient` | 48 | 1.1 % |

### Register pressure is not a `qr_svd` problem

| variant | regs | stack | spills |
|---|---|---|---|
| base `<true>` | 255 | 976 B | 248 / 248 |
| `qr_svd` stubbed | 255 | 912 B | 240 / 240 |
| `evd` stubbed | 255 | 752 B | 248 / 248 |
| twist half stubbed | **210** | 800 B | **0 / 0** |
| stretch half stubbed | **186** | 608 B | **0 / 0** |

Removing `qr_svd` leaves registers and spills essentially untouched; removing *either* stencil half
removes **all** spilling. A `qr_svd` replacement therefore wins on instruction count and divergence
with a **zero occupancy component** — which is precisely the component that would not have
transferred to the 5090.

### Correction to this round's transfer prediction for w1

The assignment table above predicted "FP64-heavy: a 1/32-rate part over-rewards this, must be
re-measured on w3 before acceptance". The probe says the opposite, and the record should carry the
correction: the available gain is fewer FP64 instructions plus removed warp divergence, both
algorithmic, with a measured-zero occupancy component. The 5090 runs FP64 at **1/64** against the
3060/3070's 1/32, so this kernel is a *larger* share of frame time on the acceptance box than on the
development box (s15 observed the same). The win should transfer at **equal or larger** relative
size, not smaller. The divergence half (~1 032 of 2 127 FP64) is architecture-independent — SIMT
lockstep is identical on 7.5, 8.6, 8.9 and 12.0.

### Robustness finding (not a perf item)

The `while` loop at `qr_svd.hpp:245` has **no iteration cap**; every other guard in the function is a
tolerance test. A sufficiently ill-conditioned `F` can spin, and it spins the entire warp. A
fixed-sweep replacement removes the failure mode as a side effect; if the rewrite is not taken, a cap
is cheap insurance.

## Probe p02 (w1-ampere) — fixed-sweep branch-free 3x3 SVD, prepared and proved but ungated

> **Status.** The change is written, it compiles against the real tree, and its numerics are proved
> on 2.5e6 randomised samples. It is **not applied to the branch** and **not accepted**: the w1
> slot's second box (RTX 3070, instance 50740303) also failed to provision, so neither the
> correctness gate nor either level of the performance gate could be run. Everything needed to
> finish it in one sitting — the patch, both harnesses, every raw number — is in
> `agent_docs/performance/data/2026-09-12-round5-w1-svd/`.

Follows probe p01, which established that `math::qr_svd` is 47.0 % of the warp-effective FP64 of
`StableNeoHookean3D` G/H and that the kernel's only backward branch is that function's
Wilkinson-shift bidiagonal QR iteration.

**Change.** `math::qr_svd_fixed<NSweeps,T>` in `algorithm/qr_svd.hpp`: 4 cyclic Jacobi sweeps
(12 exact rotations) on the normal matrix `M^T M`, then a 3-Givens QR of `M*V` for `U` and the
signed singular values, where `M = A * 2^-e` is `A` scaled by a power of two (exact) so the routine
is scale-invariant. The SNH G/H kernel gains a second template parameter `FixedSvd`;
`UIPC_QR_SVD_FIXED=0` selects the old path. Output convention is unchanged: `U,V in SO(3)`,
`S0 >= S1 >= |S2|`, `sign(S2) = sign(det A)`. `dEdF` and `project_F_gradient` are untouched
(p01: 1.1 % combined), and `gradient_only` launches return before the SVD, so **gradients and
energies are bit-identical** — only the SPD-projected Hessian changes.

### Why 4 sweeps

Measured directly, the same way p01 measured the old loop's trip count: the smallest sweep count
whose reconstruction residual is <= 1e-14, 65 536 samples per distribution.

| F distribution | mean | median | p95 | max | needing 2 / 3 / 4 |
|---|---|---|---|---|---|
| `I + 1e-4*N` | 3.06 | 3 | 4 | **4** | 2 602 / 56 191 / 6 743 |
| `I + 1e-2*N` | 3.18 | 3 | 4 | **4** | 1 021 / 51 864 / 12 651 |
| `I + 1e-1*N` | 3.23 | 3 | 4 | **4** | 659 / 49 448 / 15 429 |
| `I + 3e-1*N` | 3.24 | 3 | 4 | **4** | 608 / 48 324 / 16 604 |
| full random | 3.22 | 3 | 4 | **4** | 640 / 49 880 / 15 016 |
| `R*(I+1e-2*N)` | 3.18 | 3 | 4 | **4** | 979 / 51 777 / 12 780 |
| rank 2 (`s2 = 0`) | 3.25 | 3 | 4 | **4** | 526 / 47 818 / 17 192 |
| reflection (`det < 0`) | 3.22 | 3 | 4 | **4** | 632 / 49 875 / 15 029 |
| 2 equal singular values | 1.00 | 1 | 1 | 2 | — |
| 3 equal singular values | 1.00 | 1 | 1 | 1 | — |
| `cond(F) = 1e2` | 2.96 | 3 | 3 | **3** | — |

Same shape as p01's histogram of the *old* loop (mean 3.2, median 3, p95 4) and the same
regime-insensitivity — which is what makes a fixed count affordable. A fixed count must cover the
**max**, not the mean: 3 sweeps leaves a 3.5e-6 residual on the tails, 4 covers every one of the
~7e5 samples, 5 buys nothing measurable and costs 153 more FP64 instructions (3.4 % of the kernel).

### Numerics — rounding level, proved

Randomised verifier over the real `UIPC_GENERIC` code, new vs **the old path**, 9.6e5 host samples
at 4 sweeps across 18 families, plus 1.57e6 device samples across 12 families as a permanent Catch2
test (`apps/tests/backends/cuda/qr_svd.cu`). Device coverage matters: the fixed path calls `rsqrt`
on device and `1/sqrt` on host.

Worst case over each family, relative to `max|F|`:

|---|---|---|---|

| `I + 1e-4*N` | 2.3e-15 | 2.8e-14 | 2.2e-15 |
| `I + 1e-1*N` | 2.3e-15 | 2.6e-14 | 2.1e-15 |
| full random | 2.5e-15 | 3.0e-14 | 3.3e-15 |

`U^T U - I`, `V^T V - I`, `|det V - 1|`, the ordering `S0 >= S1 >= |S2|` and `sign(S2) = sign(det F)`
hold at <= 3e-15 / exactly, on every sample of every family.

**Where it is better and where it is worse.** For every physically reachable `F` the fixed-sweep
path is ~10x *more* accurate than the old one, and it is the only one of the two that survives
extreme scaling (the old path loses `V`'s orthogonality entirely at `|F| ~ 1e150`). The one genuine
trade is the classic normal-matrix one: reconstruction error grows as `eps*sqrt(cond(F))`, so the
paths cross at `cond(F) ~ 1e5`:

| cond(F) | 1 | 1e1 | 1e2 | 1e3 | 1e4 | 1e5 | 1e6 | 1e8 | 1e10 |
|---|---|---|---|---|---|---|---|---|---|
| new recon | 2.1e-15 | 2.1e-15 | 2.7e-15 | 4.6e-15 | 1.3e-14 | 5.4e-14 | 1.4e-13 | 1.5e-12 | 1.4e-11 |
| old recon | 1.9e-15 | 3.9e-14 | 3.9e-14 | 4.7e-14 | 5.2e-14 | 4.2e-14 | 5.0e-14 | 4.0e-14 | 3.7e-14 |
| **new dS/\|F\|** | 1.7e-15 | 2.1e-15 | 2.6e-15 | 2.0e-15 | 3.3e-15 | 2.3e-15 | 2.1e-15 | 2.6e-15 | 1.9e-15 |
| old dS/\|F\| | 1.5e-15 | 3.2e-15 | 2.8e-15 | 2.2e-15 | 2.2e-15 | 2.1e-15 | 2.1e-15 | 1.9e-15 | 1.6e-15 |

The **singular values themselves** — which is what the SNH eigenvalue formulas consume — stay at
2-3e-15 relative to `|F|` for *both* paths at *every* condition number, because they come from the
Givens QR of `M*V` rather than from `sqrt` of the normal matrix's eigenvalues. Only the singular
*vectors* degrade, and only beyond `cond(F) ~ 1e5`, which an IPC barrier does not allow a tet to
reach.

### Robustness

p01's finding stands and is fixed by this step: the `while` at `qr_svd.hpp:245` has **no iteration
cap**, and it spins the whole warp. The fixed-sweep path has no data-dependent loop at all, so that
failure mode is gone from the SNH Hessian. (The old path is still reachable via
`UIPC_QR_SVD_FIXED=0`, and is still used by `matrix_utils::svd` / `cuda_tool::eigen::pd` — see
candidates.)

proportionally less. That is a prediction, not a result, and it is exactly the thing a gate exists
to overturn.

### Cross-architecture expectation

Both halves of this gain are **algorithmic and should transfer**, and p01's correction to the
round's own prediction holds:

- **Instruction count.** Fewer FP64 ops is fewer FP64 ops on every architecture. The 5090 runs FP64
  at **1/64** against the 3060/3070's 1/32, so this kernel is a *larger* share of frame time on the
  acceptance box than on the development box — the relative win should be **equal or larger**, not
  smaller.
- **Divergence** (the ~1 032 warp-effective FP64 that the old loop's trip-count spread costs): SIMT
  lockstep is identical on 7.5, 8.6, 8.9 and 12.0, so this half is architecture-independent by
  construction.
- **Occupancy: none.** Registers (255), stack and spills (248/248) are unchanged, exactly as p01
  predicted. There is no occupancy component to label non-transferable — which is the point.

This is a *prediction from a static count*, not a measurement. It was neither confirmed nor refuted
on hardware and must not be recorded as confirmed until it is.

### Candidates after p02, with the evidence

1. **`cuda_tool::eigen::evd<Float,3>` — the 3x3 symmetric eigensolve, 470 static FP64 = 10.4 % of
   the SNH kernel (p01).** It is the *same* problem this step just solved: a symmetric 3x3
   diagonalisation. `math::jacobi_sym3_rot` from this patch already does it, and the stretch block
   `A` fed to it is a dense symmetric 3x3 with no exploitable structure. Cheapest next step in w1's
   area by a wide margin: the code exists, it needs a call-site swap, a sweep-count measurement of
   its own, and the gates. It is a *different* `evd` from w0's `make_spd<N>` (N >= 4, Eigen
   `SelfAdjointEigenSolver`) — no overlap, no file conflict.
2. **The rest of `qr_svd`'s call sites.** `matrix_utils::svd` and `cuda_tool::eigen::pd` still route
   through the iterative path, and they are what the **ARAP** constitutions call:
   `affine_body/constitutions/arap_function.h` (3 call sites),
   `finite_element/constitutions/arap_function.h` (3), and `fem_utils.cu:31`. p02 deliberately left
   them alone — they are outside w1's subsystem and switching them changes ABD. Worth profiling how
   much ARAP actually costs on `rigid-wrecking-balls` before anyone rewrites it.
3. **After p02 the stencil loop is the whole story.** The twist/flip half (1 219 warp-effective
   FP64) and the stretch half (585) are 26.9 % and 12.9 % of the *old* kernel, and would be ~38 %
   and ~18 % of the new one. Per p01 they are also the **only** things creating register pressure:
   stubbing either half drops 255 registers to 210 / 186 and removes **all** 248 B of spilling.
   That is the one remaining place in this kernel where an occupancy gain is available.

- Nothing was found in w2's (D2H) or w3's (contact) areas from this vantage point: the probe is

### Cross-architecture, cc 8.6 -> cc 12.0

p02 predicted the win transfers at **equal or larger** relative size on the 5090. This measurement is
**consistent with that prediction and does not contradict it**, but it splits the claim in two:

- **The instruction half is confirmed architecture-independent.** sm_86 reproduces the sm_75 static
  deltas to 0.1 pp (−29.9 % vs −30.0 % warp-effective FP64, −33.9 % vs −33.9 % instructions), with
  the same MUFU 102 -> 61 and the same backward-branch 1 -> 0. Nothing here is a Turing or Ampere
  artifact.
- **The divergence half is architecture-independent by construction** and was never in doubt: the
  loop is gone, so there is no trip-count spread left to pay. SIMT lockstep is identical on 7.5, 8.6,
  8.9 and 12.0.
- **There is no occupancy component to fail to transfer.** 254 registers and 200/301 LDL/STL on both
  sides on sm_86, as p01 predicted from sm_75 — the step neither gains nor loses occupancy.
- **The conversion rate is the architecture-dependent part, and it should move the right way.** On
  this 3060, −29.9 % of FP64 bought −12.8 % of kernel time, i.e. FP64 issue is roughly 43 % of what
  this kernel is waiting on at 1/32-rate FP64. A 5090 runs FP64 at **1/64**, so the same instruction
  stream spends a *larger* fraction of its time in FP64 issue and the same −29.9 % should convert at
  a *higher* rate. The prediction "equal or larger" therefore survives; what this box can say is that
  the numerator is identical and the denominator moves in the favourable direction.

What this box **cannot** say is how large the end-to-end number will be on a 5090: −1.73 % / −2.16 %
here is the product of the conversion rate *and* this kernel's share of the frame, and both change.
It should not be recorded as a 5090 figure.

## Step s26 (w1-ampere) — the `StableNeoHookean3D` G/H stencil loop: what the "spills" really were

Measured on `perf/round5` at **`d3f3a553`** (i.e. with w0's s19/s21, w2's s22 and w3's s20/s24 in the
same build), RTX 3060, cc 8.6, CUDA 12.8, driver 580.173.02. w2's s25 (contact part 1) landed after
this build and is **not** in the measured binary; it touches no FEM constitution and the merge is a
clean fast-forward on this file.

### The premise was half right, and the half that was wrong is the useful part

The brief inherited probe p01's attribution: the stencil loop "is the sole source of the spilling"
(stub either half and the 248/248 spill bytes go to zero), and therefore relieving its register
pressure should buy an occupancy win. Two things are wrong with that, and `ptxas -v` on the current
head says both immediately:

| `<HoistStretch, FixedSvd>` instantiation, sm_86 | stack frame | spill stores | spill loads | registers |
|---|---|---|---|---|
| `<false,false>` | 704 B | **0** | **0** | 250 |
| `<false,true>` | 656 B | **0** | **0** | 248 |
| `<true,false>` | 896 B | **0** | **0** | 254 |
| **`<true,true>` (shipped)** | **848 B** | **0** | **0** | **254** |

1. **There is no register spilling.** Every instantiation reports 0 bytes of spill stores and 0 bytes
   of spill loads. The 848-byte frame is thread-local **arrays**, not spilled registers.
2. **The arrays are in local memory because the old loop indexed them with a data-dependent index.**
   `sa[left][k]` and `sw[m][left]`, where `left`/`right` come from `if(tet(left) > tet(right))`.
   ptxas cannot register-allocate an array with a runtime index, so it puts the whole array in local
   memory — and that is where all 200 `LDL` / 301 `STL` come from. Stubbing either stencil half made
   the spilling "disappear" in p01 because stubbing it removed the *array uses*, not because the half
   was consuming registers.

### The change

Assemble every 3x3 stencil block in the **canonical** `(a, b)` orientation — `sum_m l_m w_m_a w_m_b^T`
with `a`, `b` compile-time constants — and transpose at write time (branch-free, by selecting the
nine entries; a data-dependent `if` there would add ten divergent branches the old loop did not
have). Then **derive the four blocks that touch node 0 instead of assembling them**:
`tetrahedron_shape_gradients` builds `g_0 = -(g_1 + g_2 + g_3)` and every `w` is linear in `g`, so
`sum_k w_m_k = 0` and `H_0b = -(H_1b + H_2b + H_3b)` exactly. Nine adds replace ~190 FP64 ops per
block. `H_00` is recovered as `-(H_01^T + H_02^T + H_03^T)` and **explicitly symmetrised**: the direct
form is exactly symmetric term by term and the derived one is only symmetric to rounding, and the
linear system assumes a symmetric diagonal block.

`Stencil2` is a template parameter, not a runtime flag (the s14 lesson); `UIPC_SNK1_STENCIL2=0`
selects the old loop. `UIPC_SNK1_HOIST_STRETCH` has no effect when `STENCIL2=1` (the new path is
always the hoisted form — it is the only one that keeps every `sw` index constant); the SASS for
`<false,true,true>` and `<true,true,true>` is identical, which is the audit of that.

### Cross-architecture

- **The gain is algorithmic and should transfer.** −25.4 % FP64 and −13.6 % instructions are
  properties of the source; s23 already showed that this kernel's static forecast made on sm_75
  reproduced on sm_86 to 0.1 pp. The 5090 runs FP64 at 1/64 against the 3060's 1/32, so the kernel is
  a *larger* share of the frame there and the relative win should be equal or larger.
- **The occupancy component is exactly zero and is measured, not argued**: 254 registers both ways, 0
  spill bytes both ways, and the memory-only intermediate above bounds the whole
  register/stack/local-memory contribution at **−0.35 %**. This is the category the brief warns
  transfers unevenly, and here it is bounded at a third of a percent — so the uneven part of this
  step is negligible on any architecture.
- **What is architecture-dependent is the conversion rate**, and it is not a constant (below). On a
  part with a relatively faster FP64 pipe the same instruction removal converts to less wall time.

### What the three data points actually say about the conversion rate

| step | static FP64 | measured kernel wall | "conversion" |
|---|---|---|---|
| s23 | −14.9 % static (−29.9 % warp-effective) | −12.8 % | 0.86 static / **0.43** warp-effective |
| s26 intermediate (memory only) | **0 %** (LDL −68 %, stack −45 %) | −0.35 % | — |
| s26 | −25.4 % | −6.60 % | **0.26** |

The 0.43 recorded after s23 is not a constant, and the reason is arithmetic, not physics: a
conversion *ratio* is the FP64 pipe's share of the kernel's time, and that share necessarily falls as
you remove FP64. Expressed absolutely the two steps agree: on case2 this kernel costs

- s23: 0.7676 ms/Newton-it removed for 1 358 warp-effective FP64 instructions = **5.7e-4 ms per instruction**
- s26: 0.3458 ms/Newton-it removed for 807 FP64 instructions = **4.3e-4 ms per instruction**

— the same number to 30 %. A consistency check from the other side: 159 870 tets = 4 996 warps,
2 376 FP64 each, at 8 SM-cycles per warp-wide FP64 instruction (1/32 rate, 28 SMs, 1.78 GHz) is
**1.9 ms of the 4.89 ms** the kernel now takes, i.e. the FP64 pipe is ~39 % occupied and the measured
marginal conversion of 0.26 is ~0.66 of that. The same arithmetic at the s23 baseline gives 61 %
against a measured 0.43 — again 0.7.

**The calibration to carry forward is therefore: this kernel converts removed FP64 at
~4.3e-4 ms/Newton-it per instruction on case2 (~2.1e-4 on mas-bunny), and the ratio form of that
number shrinks every time somebody uses it.** And the corollary that re-prices the remaining work:
of the 4.89 ms this kernel now costs on case2, **only about 21-39 % is FP64 arithmetic**. Removing
*all* of the remaining 2 376 FP64 instructions would buy at most ~−2.9 % of the case2 frame.

The win **saturates at 12 warps**, and `(128, 3)` is the cheapest way to get there. It also helps the

Note what this says with the intermediate above: ptxas spends **1 104 bytes of frame and ~1 650 bytes

statement as "local memory is nearly free on this kernel" read from the other end. Two independent
measurements now agree that this kernel's problem is **latency hiding, not memory traffic and not
instruction count**.

**Caveat, and it is the brief's own warning**: this is the category that transfers unevenly. R3 in
this round rejected s17's `__launch_bounds__(192, 2)` on the *contact* kernel when re-tested on
cc 12.0. Any such step must ship behind a switch and be re-measured on the acceptance box.

**2. Do not chase the remaining 464 B of local memory.** It belongs to `qr_svd_fixed` / `evd<Float,3>`
(the `<0,1,1>` instantiation, which has no `sw` at all, lands at the same 464 B). The memory-only
intermediate measured that traffic at **−0.35 % per 136 removed LDL**, so the whole residual is worth

**3. `evd<Float,3>`, re-priced.** It is 470 static FP64 of the 2 376 the kernel now has. At the
measured 4.3e-4 ms/Newton-it per FP64 instruction that is ~0.20 ms of the kernel's 4.89, i.e. −4 % of
the kernel and **−0.6 % of the case2 frame if it were free** — so a *cheaper* 3x3 symmetric solver is
worth perhaps half of that. Still marginal, and it is now behind candidate 1 by a factor of five.

**4. The Hessian triplet writes are fully uncoalesced — a finding in the linear-system area, not
mine.** `H3x3s(I * 10 + k).write(...)` stores into `m_values[index]`, so thread `I` writes 10 x 72 B
at byte offset `I * 720`: **consecutive lanes are 720 bytes apart**, and every 32-lane store touches
32 distinct sectors instead of 4-8. 159 870 tets x 720 B = 115 MB of Hessian per launch on case2, and
the index arrays on top. A block-major layout (`k * n + I`) would coalesce perfectly and is a change
to `TripletMatrixViewT` / the matrix assembler, which several constitutions and the contact kernels
share — i.e. it is the coordinator's to assign, and it would pay everywhere at once, not just here.
This is offered as an observation with the layout arithmetic, not as a measurement: I did not test it.

## Step s27 (w1-ampere) — `StableNeoHookean3D` G/H is occupancy-bound, and that is worth more than all of its arithmetic

s26's candidate 1, gated. Same box, same build system, measured on top of s26 (the `old` arm here is
`UIPC_SNK1_OCC=0`, which reproduces s26's committed numbers to 0.1 %).

### What the previous three measurements had cornered

| what was removed | how much | kernel wall |
|---|---|---|
| s23: a divergent loop + 41 MUFU + 558 FP64 | −14.9 % static FP64 | −12.8 % |
| s26 intermediate: 136 LDL, 384 B of frame, 14 registers | **no arithmetic at all** | −0.35 % |
| s26: 807 FP64 and a third of the local traffic | −25.4 % static FP64 | −6.6 % |

A second `__global__` wrapper over the same `__device__` body, carrying `__launch_bounds__(128, 3)`.
`UIPC_SNK1_OCC=0` selects the unbounded one. The body was moved into

### Numerics — bit-identical, proved at the PTX level

Both wrappers instantiate the same `__device__` body. Their PTX entry function bodies are
**164 874 bytes each and byte-identical** after normalising only five things that carry no
semantics: the mangled entry symbol, basic block label numbers (`$L__BB13_x` vs `$L__BB15_x`),
`callseq` numbers, the local depot symbol's number (`__local_depot13` vs `__local_depot15` — the
depot itself is 448 bytes in both), and the `.maxntid` / `.minnctapersm` directives, which are the
whole point of the change. The check and its output are archived
(`harness/ptxdiff.py`, `raw-s27/ptx_identity.txt`). Everything ptxas does
after that is register allocation and spill insertion, which does not reassociate arithmetic and
cannot change FMA contraction (contraction is already fixed in the PTX). Corroborated in the SASS:
the FP64 instruction multiset is identical instruction for instruction (DFMA 1402, DMUL 678, DADD
205, DSETP 91, MUFU 61 in both); only `LDL`/`STL` differ.

−0.14592149 / −0.14592207 / −0.14592189 new against −0.14592056 / −0.14592186 / −0.14592148 old —

The brief's own warning applies in full, and this round already has the precedent: **R3 rejected

trade-off here is "spill traffic for warp slots", and both sides of it are architecture specific:

- sm_86 (this box): 65 536 registers and 48 warp slots per SM; unbounded = 254 regs = 8 warps = 17 %

- The acceptance box (cc 12.0, 5090) runs FP64 at **1/64** against this part's 1/32, so the kernel is

This is exactly why the step ships behind `UIPC_SNK1_OCC`. **The coordinator should re-measure it per
architecture and, if it costs on cc 12.0, either default it off there or make the bound
architecture-conditional** (`__CUDA_ARCH__` already gates that trivially since the bound is a
compile-time attribute). s26 carries no such caveat — it is pure instruction removal.

## Cross-architecture observations
- **The hinge is the round's second measured divergence, and it inverts the first.** The same
  geometry change (48,256) -> (380,32) gave w0 **−23.3 %** on cc 7.5 (40 SMs) and w3 **−15.4 %** on
  cc 12.0 (36 SMs). The cause is wave quantisation: 48 blocks on 40 SMs is 1.2 waves rounded to 2
  (a 67 % penalty), on 36 SMs it is 1.33 rounded to 2 (50 %). **The gain is an arithmetic accident of
  the SM count — architecture-dependent in size, never in sign.** On a 5090 the hinge is 0.28 waves,
  i.e. squarely in the never-reaches-the-SMs regime, so it should gain *more* than either measurement.
- **s24 splits its own transfer prediction per site**, which is the most falsifiable claim the round
  will hand the acceptance run: *more* on a 5090 for every grid-1-to-5 site (half-plane
  assemble/energy, bdf1 kinetic G/H, `feasible_step_PT`, contact energies k1/k4 — they hold 0.6-3 %
  of a 170-SM device against 3-14 % here); *less* where the parallelism ceiling binds — 576 bodies =
  18 warps = at most 18 SMs, which is 50 % of this box but **11 % of a 5090**, so `ortho_potential`,
  `abd_diag` and `kinetic_shape_k2` cannot regress but will not grow either.
- **w0 on s21: the standard transfer warning is inverted here.** This is not per-SM occupancy
  tuning — resident warps per SM are unchanged (8 either way at 255 registers). It is
  grid-size-against-machine-size, which gets **worse on a bigger GPU**. On a ~170-SM 5090 the
  unfixed kernels reach 3/170 and 48/170 SMs, and `fitted_block_dim` returns 32 there too, so w0
  expects **more** than its −23 % / −65 % on the acceptance box. w3 makes the same argument for s20
  from cc 12.0. Two architectures predicting the same direction for the same mechanism is the
  strongest transfer claim in the round — and the acceptance run can falsify it cleanly.

- **A documented cc 7.5 <-> cc 12.0 sign flip (R3), the round's first.** The same
  `__launch_bounds__(192, 2)` on contact part 2, measured on both architectures:

  | | 2070S (round 4, s17) | 5060 Ti (round 5, R3) |
  |---|---|---|
  | part 2 (receives the bound) | −3.4 % | −1.9 % (in scatter) |
  | part 1 (concurrent across the K9 fork) | **+5.8 %** | **−4.9 %** (disjoint) |
  | union per iteration | **+5.9 %, net loss** | **−3.9 %, net gain** |

  On Turing part 2's extra warps steal SMs from part 1; on Blackwell the narrower blocks leave part 1
  more room, and part 1 is the half that moves. This is precisely the category the brief warned is
  least transferable, and it is now measured rather than asserted. It is also why w3 chose grid
  *shape* over occupancy for its accepted step.
- **s20 is the opposite case: structural, and it grows with the GPU.** A grid of 3 blocks is not an
  occupancy-tuning problem, it is a launch that never reaches the SMs. A 5090 has ~170 SMs, so at
  base these launches occupy 3/170 ~ 1.8 % of the device and the spread should pay **more** there.
  It cannot regress a smaller GPU — when the natural grid already covers the device the helper
  returns the old geometry unchanged, which is why case2 and mas-bunny are exactly neutral.
  **Caveat from w3:** on a 36-SM box the spread is capped by body count (576 threads = 18 warps ->
  at most 18 SMs) and one warp per SM reaches only ~28 % of an SM's throughput, so the win
  saturates; more bodies, or more parallelism per body, would extend it.
- **The kernel ranking itself shifts with architecture.** On cc 12.0 contact part 2 is 9.0 % of

- **s19 (w0, cc 7.5)** splits into a code-shape half (same FLOPs, fewer instructions, no out-of-line

  show less than −15 % / −8 % per launch.** The 192-register drop may buy occupancy on some
  architectures and none on others. Nothing should regress: no launch config, no algorithm and no
  scene changed.
- **R1 is a working-set result, not an architecture result**, and it sets a size rule the other
  workers can use directly: a register-resident eigen-solve wins while the working set fits

  mechanism is not** — worth re-testing on the acceptance box before generalising.
- **This is why w1's p02 is not in conflict with R1**: p02 replaces a *3x3* SVD (tiny working set,

## Convergent discovery, and the duplication it cost (coordinator note, 13:25)

**w0 (cc 7.5) and w3 (cc 12.0) independently diagnosed the same root cause, on different kernels,
within ninety minutes of each other**: `best_block_dim` is `cudaOccupancyMaxPotentialBlockSize`,
which maximises warps *per SM* and is blind to how many SMs the grid reaches. Neither was told about
the other's finding, and w0's assignment (a warp-cooperative solve) and w3's (occupancy tuning of
contact part 2) both pointed elsewhere — each profile redirected its own step. w0 reports the
pathology is structural: `best_block_dim` is used at **every named launch site in the backend**.

That convergence is strong evidence. The duplication it produced is the real cost of running workers
in parallel, and it should be recorded as such:

- **Two helpers for one problem.** w3's `cuda_tool/spread_launch.h` (`spread_block_dim`, one warp per
  block when the grid does not cover the device) and w0's `utils/proj_launch.h` (`fitted_block_dim`,
  halve while below 8 blocks/SM). Their *measurements agree* — w3 measured block 32 best (64 ->
  0.9205, 96 -> 0.9882 against 0.8500 ms/it) and w0's fit lands on 32 at every site — so they differ
  in shape, not in outcome, so far.
- **Two fixes for one call site.** Both fixed `ortho_potential` G/H, by different routes. w0's branch
  additionally fixes the **`DiscreteShellBending` hinge** (−23.3 %), which s20 does not touch; s20
  additionally fixes `abd_diag_preconditioner` and the ortho *energy* kernel, which w0 (having merged
  before s20 landed) still reports as unfixed and unowned.
- **Resolution**: w3 owns the consolidation as part of its in-flight sweep — one header, one
  heuristic, one env switch, with the criterion stated. `s21` is therefore **recorded but held out of
  `perf/round5`** until that lands; merging two competing helpers first and reconciling later would
  put a build in the tree that nobody measured.
- **Method lesson for `PERF_METHOD.md`:** disjoint *subsystem* ownership does not imply disjoint
  *root causes*. A cross-cutting pathology surfaces in several workers' areas at once, and parallel
  workers will each solve it locally. Either the coordinator hoists it to one owner the moment the
  second worker reports it, or the round pays for the duplicate. Numbering collided too — both
  workers called their step `s20` — because step ids were handed out per worker rather than centrally.

## Why s22 is a *marginal* accept, and what it corrected (coordinator, 13:35)

The brief's rule 4 says a gain inside run-to-run noise is not a gain. s22 sits exactly on that line and
the verdict should be legible later, so: **accepted**, on these grounds and no stronger ones.

- The **targeted scope moves decisively and identically on all four scenes** (−16 to −19 % readbacks,
  −14 to −25 % GPU-idle stall). That half of the two-level gate passes without qualification.
- The **end-to-end effect is real but at the edge of measurability**: −0.23 % on mas-bunny, which is
  deterministic (Newton 465 in all six runs) and whose same-arm spread is 0.08 ms against a 0.12 ms
  delta, and −0.36 % per Newton iteration on case2 with counts controlled. On the two scenes where
  counts are *not* controlled it is inside noise. The sign is consistent everywhere and **no scene
  regresses**.
- The change is **value-identical, proved**: 860 readbacks compared byte-for-byte through both paths
  on mas-bunny with 0 mismatches, and 2 000+ counter comparisons per scene across three scenes with
  0 mismatches. Same counters at the same stream point means the same capacity decisions and the same
  candidate sets, so there is no trajectory risk to weigh against the small gain.
- It leaves behind **the instrument**, which the round did not have: nothing in the codebase could
  previously separate drain from stall, and that distinction is what showed round 4's estimate was
  too high.

**The correction matters more than the step.** Round 4's s14 gap attribution put this candidate at
1.3-3.0 ms per frame of GPU idle on every scene. Measured properly on cc 8.9 it is **0.556 / 1.046 /
1.215 / 1.627 ms per frame = 0.9-2.3 % of frame time**, and per readback 5.9-10.4 us rather than
14-22 us — round 4's nsys gap also contained host decision time and relaunch, which this host partly
hides. **The D2H item was overvalued on the round-4 pick list by roughly 2x**, and its remaining
ceiling after s22 is ~1.5 % of frame even if every remaining readback were free. Future rounds should
price it accordingly rather than inheriting the old estimate.

**The one large item left in the host pipeline is not in the solver at all**: the
`event_write_scene` readback in `FiniteElementMethod` moves 460 KB of pageable memory once per frame
and is **388 us/frame — 53 % of all stall in the pipeline**. It is now pinned but still a full
end-of-frame serialisation. Taking it needs an application-semantics decision (whether vertex state
may be one frame late), which is why w2 correctly did not take it unilaterally.

## The conversion rate: a static FP64 delta is a ceiling, not a forecast (w1, s23)

The most useful number s23 produced is the one that **undershot its own forecast**, and it should be
read before any future step is sized from instruction counts.

- p02 measured −29.9 % of warp-effective FP64 and forecast roughly −4.2 % of the case2 frame.
- s23 measured **−12.8 % of kernel wall time and −1.73 % of the frame**.
- **Conversion rate ~0.43**, and the mechanism is visible in the same disassembly table: **`LDL 200 /
  STL 301` are unchanged**. p01 had already attributed this kernel's spilling to the *stencil loop*,
  not to `qr_svd` — so removing a third of the arithmetic removes **none** of the memory traffic that
  the removed arithmetic was interleaved with.

This is not a rejection: the kernel moved, both target scenes moved, the distributions are disjoint
and the controls are flat. It is a **calibration**. Round 5 now has a measured exchange rate between
the static-analysis method that p01/p02 pioneered and wall-clock reality on this kernel class:
**about 0.4**. p01's technique is still the cheapest way to rank stages — it found the right target
and predicted the instruction delta to 0.1 pp across two architectures — but its output is an upper
bound on the achievable wall gain, and the gap is whatever else the kernel is waiting on.

Applied immediately: w1's own next candidate, `evd<Float,3>` at 10.4 % static, sizes to ~4 % of
kernel and **<1 % of frame** at this conversion rate, which is why it is recorded as marginal rather
than picked up.

## Provisioning defect: a vacuous correctness gate (found by w1, 14:00)

`baseline_tests.txt` on a freshly provisioned box recorded `pytest rc=2, 7 errors during collection`
on **w1's and w2's boxes but not w3's** — the image carries `libX11.so.6` on some hosts and not
others, and `pyuipc` links it, so every `sim_case` python test failed to import. A baseline captured
in that state makes **the python half of every later correctness gate vacuous**: a worker comparing
"7 errors" against "7 errors" sees identical counts and concludes nothing changed.

- **Impact, checked on every box rather than assumed**: w3's baseline was valid (`pytest rc=0, 48
  passed`, libX11 present from the start), so s20's gate stands. w2's baseline was broken, but w2
  noticed the discrepancy and its own gate runs reported 48 passed — verified by the coordinator
  re-running pytest on that box (48 passed, 1 skipped, and the library is present), so **s22's gate
  stands too**. w1 installed the X11 libraries, re-baselined pytest at the base build (48 passed / 1
  skipped, matching w0's local figure), and kept the original as `baseline_tests.orig.txt`.
- **Fixed in `tools/vast/vast_remote_dev_setup.sh`**, two ways: the X11/GL runtime libraries are now
  installed explicitly, and provisioning **fails** unless every suite in the baseline returns rc=0.
  Handing a worker a broken gate reference is worse than failing to provision the box, because the
  failure is silent and survives into the ledger.

## The warp-boundary defect s21 would have shipped (w3, s24)

Holding `s21` out of the tree pending consolidation turned out to matter for a reason nobody
anticipated. w0's `fitted_block_dim` **halves the block size**; `best_block_dim` returns 640, 768 and
896 at real sites in this backend, so repeated halving gives `640 -> 320 -> 160 -> 80 -> **40**` —
block sizes that **straddle warp boundaries**. That changes warp composition, and therefore
`__activemask()`, and therefore the bit-identity argument that the whole grid-spread family rests on.

s24 halves the **warp count** instead, so warp *k* always covers items `[32k, 32k+32)` whatever the
block size. Same ramp criterion, same measured answer at every site either helper was tested on — but
only one of the two is safe next to warp primitives.

Two workers converging on one root cause produced one correct helper and one subtly unsafe one, and
the only thing that caught it was making a third party consolidate them before either shipped.

## What bit-identity cost to prove, and why it is worth recording

s24's verifier runs each instrumented site twice per invocation (occupancy-max geometry -> D2D
snapshot of every output region -> shipped geometry -> device-side word compare):
**981 903 659 words on wrecking-balls and 859 017 511 on cube-wall, 0 mismatching.** Two obstacles
had to be solved rather than argued around, and both are reusable knowledge:

- Comparison is in **32-bit** words because a `TripletMatrixView`'s index arrays are `int*` at an
  arbitrary triplet offset — an 8-byte load off them faults (found via a sticky `misaligned address`).
- `assemble_dytopo_effect_pair_k3` **accumulates** into `diag_hessian` and is therefore not
  idempotent, so the verifier gained a save/restore phase for declared in/out buffers rather than
  skipping the site.

**Sites deliberately not touched, with reasons** (this list is the step's other output):
contact `do_assemble` (`__any_sync`, already grid 26-31, and a throughput change to the suite's
largest kernel needs its own step), `ee_mollifier_partition_kernel` (its `atomicAdd` allocates the
output slot, so it is **order-dependent and not bit-identical under any geometry change**), the s05
`pair_warp` kernel (`__shfl_sync` + atomics), `buffer_fill_kernel` (shared `cuda_tool` infra),
`fused_pcg_scalar_kernel` (`<<<1,1>>>`, no parallelism to spread).
